 TinyRat

> Первая серьезная попытка собрать собственную embedded-платформу на RP2040: с UI, приложениями, USB-сценариями и работой с файлами.

## О проекте

**TinyRat** - это embedded-система на RP2040 со своим графическим launcher'ом, модульными приложениями, USB-функциональностью устройства и ресурсами, загружаемыми из файловой системы, построенная на творческой версии BadUSB, спроектированной Роболабой московского кампуса Школы 21 от Сбера.
Посмотреть их другие интересные устройства вы можете в их [репозитории](https://github.com/RoboLab21), а подробную схему платы посмотреть [здесь](https://github.com/Freimor/HRDW-Automaton_v3).

Идея проекта была не в том, чтобы написать один демонстрационный firmware-модуль, а в том, чтобы собрать маленькую самостоятельную платформу: со своим UI, логикой запуска приложений и реальным взаимодействием с внешним миром через USB и файлы.

В этом репозитории сочетаются сразу несколько направлений:

- архитектура embedded-прошивки;
- легковесный интерфейс на самом устройстве;
- модель приложений;
- USB composite-сценарии;
- загрузка ресурсов из хранилища;
- keyboard automation workflow.

## Зачем это сделано

Этот проект задумывался как portfolio-репозиторий, но одновременно и как реальный учебный опыт. Это моя первая серьезная попытка работать с железом на таком уровне, поэтому некоторые части сделаны довольно прямо, а где-то наверняка не самым лучшим способом.

Мне важно сказать это честно: почти наверняка существовали более правильные, более красивые или более эффективные способы реализовать отдельные решения. Но этот репозиторий показывает живую работающую систему, реальную интеграцию нескольких подсистем и попытку собрать цельный embedded-продукт, а не абстрактный toy example.

Любой может переосмыслить, переработать, расширить или улучшить отдельные части по-своему. В этом тоже часть идеи: проект должен быть понятным, hackable и пригодным для дальнейшего развития. Так же не были задействованы ряд представленных на плате возможностей вроде поджимных контактов соединенных со свободными GPIO микроконтроллера для интеграции дополнительных модулей, а так же не использовались встроенные 16МБ памяти. Все это открывает еще больше возможностей для кастомизации и дополнения.

## Возможности

- **Композитное USB-устройство (HID + MSC)** - TinyRat всегда виден как клавиатура (и мышь), а доступ к диску включается только в disk mode.
- **Работа с файлами и ресурсами через FatFS** - скрипты, изображения и другие данные читаются из файловой системы, а не зашиваются полностью в прошивку.
- **Приложение сценариев (scen_app)** - показывает список текстовых сценариев с SD-карты, позволяет пролистывать, выбирать и запускать нужный сценарий автоматона.
- **Интерактивный inject-режим** — выполняет выбранный сценарий: построчно читает его из файла и отправляет команды на хост как USB HID-клавиатура.

## Архитектурный фокус

Самое интересное в проекте - это сочетание нескольких задач внутри одного небольшого устройства:

- embedded UI и переходы между состояниями;
- архитектура приложений;
- USB descriptors и поведение режимов;
- ресурсы, завязанные на файловую систему;
- практические automation-сценарии.

Именно это сочетание для меня важнее, чем идеальная полировка реализации. Ценность проекта - в том, что он показывает системное мышление на стыке firmware, хранения данных, UX маленького устройства и host-device взаимодействия.

## Сборка

В репозитории уже лежат `CMakeLists.txt` и `pico_sdk_import.cmake`, поэтому если Pico SDK и расширение **Raspberry Pi Pico Project** в VS Code настроены нормально, то достаточно открыть проект через плагин и собрать его оттуда. 

Типичный ручной flow тоже должен быть привычным для Pico SDK:

```bash
mkdir build
cd build
cmake ..
make -j
```
Если просто хочется начать - в папке extra вас ждет uf2 файл, скопируйте его на плату, поключенную в режиме BOOT, затем распакуйте архив resourses.tar, скопируйте содержимое в корень SD карты, вставьте карту и пользуйтесь!

## Структура системы

Проект устроен не как один большой сценарий, а как маленькая платформа с разделением на несколько уровней:

- **hardware layer** - драйверы дисплея, тач-контроллера, SD и других периферийных компонентов;
- **system / firmware layer** - базовая логика платформы, общие сервисы, цикл работы системы;
- **UI layer** - окна, слои, отрисовка ресурсов, экранные переходы;
- **application layer** - отдельные приложения, которые запускаются из launcher'а;
- **storage / USB layer** - работа с файлами, ресурсами и взаимодействием с хостом через USB.

## Логика работы

После запуска устройство инициализирует базовые подсистемы и переходит в основной system loop. Базовая прошивка предоставляет приложениям общий runtime: экран, события ввода, доступ к ресурсам и файловой системе, а также USB-поведение.

Центральная точка входа для пользователя - launcher. Он отображает доступные приложения как отдельные сущности интерфейса и позволяет запускать их прямо с устройства, без внешнего управляющего ПО.

## UI-модель

Интерфейс строится вокруг слоёв (`layer`) и подслоёв (`sublayer`), их список реализован как стек. Это позволяет не просто перерисовывать весь экран заново, а собирать его из отдельных логических частей: базового фона, overlay-элементов, кнопок подтверждения и других визуальных блоков.
Любая операция, которая меняет дерево слоёв (`create_layer()`, `add_sublayer()`, `pop_node()`, `collapse_list()`) сразу вызывает перерисовку (`build_with_res()`), которая отрисовывает root node и его sublayers; если `res_name != NULL` - загружает картинку в `framebuf` и вызывает `load_buf()`, иначе - рисует цветной прямоугольник.
Типичный сценарий такой: основной экран приложения существует как базовый слой, а временные элементы интерфейса - например, confirm-overlay - добавляются поверх него как отдельный слой с собственным подслоем-кнопкой. После закрытия overlay базовый экран остается концептуально тем же экраном, а не пересобирается как другой режим с нуля.

## Принятые соглашения

В проекте есть несколько намеренно принятых ограничений, которые упрощают поведение системы и помогают избежать ошибок:

- каждый обычный `layer` может иметь свои `sublayer`;
- `sublayer` по структуре похож на обычный `layer`, но не должен иметь собственные `sublayers`;
- это ограничение принято сознательно, чтобы не усложнять идею принадлежности к слою, освобождение памяти и жизненный цикл UI-узлов;
- попытка строить вложенность глубже одного уровня может привести к некорректному освобождению памяти и утечкам;
- overlay-слой должен логически перехватывать ввод, чтобы нажатия не проходили сквозь него к нижележащему экрану;
- приложения используют общую архитектуру жизненного цикла: вход, обработка событий, периодический tick и выход;
- переключение приложений происходит через `app_open`, который не позволяет запустить поверх приложения себя самого, если требуется запустить приложение заново, то следует исполнять `app_name.exit()` и `app_name.enter()` или же предусмотреть очистку состояния хранилища данных приложения `app_name.ctx` в `app_name.enter()`;
- координаты получаемые контроллером сенсора, могут отличаться от реальных координат касания на вашем дисплее, поэтому маппятся через подобранные эмпирически поправки;
- при обработке событий - кнопки имеют приоритет над касаниями;
- SD карта должна быть SDHC, отформатированная в FAT32 MBR;
- одновременная работа устройства и подключенного компьютера с SD картой запрещена из за нестабильности и риска повреждения файловой системы; 

## Inject сценарии

С точки зрения формата, сценарий - это обычный текстовый файл, читаемый построчно через FatFS. Каждая строка либо печатается как текст, либо интерпретируется как клавиатурная команда, если начинается с `KEY` (если вам в строке необходима именно последовательность KEY - просто поставьте пробел в начале строки).
Сценарии хранятся в каталоге: `/apps/scen_app/scripts`.

Есть два типа строк:
- Обычный текст - строка отправляется как последовательность нажатий символов.
- Команда `KEY...` - строка интерпретируется как набор специальных клавиш и/или модификаторов.

После отправки строки идет ожидание 1500мс чтобы система успела выполнить указанные действия.

Синтаксис: `KEY <спец-кнопки и модификаторы>[+<обычные символы>]`
До "+" поддерживаются такие модификаторы:

- `W` → Left GUI / Win / Meta;
- `S` → Left Shift;
- `C` → Left Ctrl;
- `A` → Left Alt.
До "+" также поддерживаются специальные клавиши:
- `1..0` → F1..F10;
- `-` → F11;
- `=` → F12;
- `E` → Enter;
- `e` → Escape;
- `T` → Tab;
- `D` → Delete;
- `B` → Backspace;
- `s` → Space;
- `I` → Insert;
- `P` → Print Screen;
- `{` → Arrow Up;
- `}` → Arrow Down;
- `[` → Arrow Left;
- `]` → Arrow Right;
- `^` → Page Up;
- `v` → Page Down;
- `H` → Home;
- `N` → End;
- `X` → Caps Lock;
- `M` → Menu.

Важное уточнение: в конце каждой строки в текстовом файле сценария стоит "\n" при переводе на новую, что соответственно будет интерпретировано как нажатие клавиши ENTER, поэтому одно цельное действие нужно писать в одну строку и отдельно отправлять команду на нажатие ENTER не требуется.
Примеры команд:
- KEY W+r               - открытие окна "выполнить" в Windows 
- notepad               - будет написана строка в окно
- Hello From TinyRat!   - будет написана строка в notepad
- KEY C+s               - будет вызвано диалоговое окно сохранения файла
- KEY E                 - будет нажата клавиша ENTER
- KEY A4                - окно notepad будет закрыто

## Ресурсы

Для создания собственных ресурсов используйте `conv2fullscreen` и `conv2small` из папки `extra`. Эти утилиты предназначены для конвертации полноэкранных и уменьшенных изображений соответственно в используемый проектом формат ресурсов — массив последовательно идущих пикселей в RGB565.

Поддерживаются входные изображения в форматах `.jpg`, `.jpeg` и `.png`.

- **Использование:** выполните в командной строке `./conv2small resource.png resource.res`
- **Важно:** изображения нужно заранее подготовить, уменьшив их до `240x280`
- В случае `conv2small` можно использовать другие размеры, но они должны быть меньше `240x280`.
